胸部 X 光，10 类多标签。一张图可以同时有几个征象，也可以一个都没有。数据按 study 组织，一个 study 可能有几张不同体位的图，而提交是按 study 算的。

比赛规则只许用主办方给的数据。我把这条往前推了一步：预训练权重也不用。DenseNet121 从 `weights=None` 开始，6.96M 参数全部自己初始化。

下面讲清三件事：代码怎么分层、每层吃什么吐什么、怎么确认它真的能跑。

## 一、三条规则决定了做法

| 规则 | 意思 | 所以怎么做 |
| --- | --- | --- |
| 主指标是 Macro-AUC | 每个类一样重要，稀有类不能拖后腿 | 每个类单独算 AUC；监控项就是它；损失给稀有类加权，但设上限 |
| 提交按 study | 每个 study 都要输出全部 10 个类 | 训练看单张图，评测和推理按 study 合并 |
| 只能用主办方数据 | 不并别的数据集，不加载预训练权重 | 只能靠初始化、正则、更长的训练把效果挣出来 |

Macro-AUC 只看排序，不看阈值。所以调阈值让 F1 变好，AUC 一点不动。工程里 `submission.threshold` 只影响写进文件的 Gate 列，不参与选模型。

调用方向只有一个：入口调执行，执行调基础。反过来没有一处。

这带来三个好处：

- **训练代码不知道谁在拉它。** 同一个 `run_training`，可以被命令行直接调，可以被调度器当子进程拉，也可以被 `torchrun` 拉成 N 个进程。判据是环境变量，不是开关。
- **推理不用看训练配置。** 预处理参数、类别顺序、分辨率全从断点文件里读。所以 224 训的模型和 320 训的模型能放进同一个集成，各自按自己的尺寸处理。
- **调度层不碰训练。** `server/` 里没有一行 import `torch`。它只负责拼命令、分卡、收产物。所以调度服务可以在没装 torch 的机器上跑。

## 三、配置怎么写

配置是唯一的参数来源。代码里没有写死的数字。

分三层：`base.yaml` 放公共默认值，`gear/*.yaml` 只放和机器有关的项，`train/*` 和 `infer/*` 是具体配方，用 `_base_` 继承上一层。

```mermaid
flowchart LR
  BASE["base.yaml<br/>公共默认值"] --> RECIPE["train/ 与 infer/ 配方"]
  GEAR["gear/ 机器档位"] --> RECIPE
  RECIPE --> MERGED["合并后的配置"]
  SET["--set 覆盖"] --> MERGED
  MERGED --> CHECK["加载时检查"]
  CHECK -->|"通过"| RUN["训练 / 推理"]
  CHECK -->|"不通过"| ERR["报错，并猜你想写哪个键"]
```

四条规矩：

- **继承可以套多层，有环就报错。** 相对路径按引用它的文件所在目录算。
- **路径都相对项目根。** 从哪个目录启动，产物都落在同一处。
- **`--set` 写错键当场报错，YAML 里写错只提醒。** 命令行是人在敲，立刻纠正最省时间；YAML 可能是继承链上别人写的，直接失败会卡住整条链。`--set train.epochz=30` 会在开跑前就被拒绝，不会等 30 个 epoch 跑完才发现。
- **加载时一次检查完。** 类别数是否一致、通道数是否配得上、几个参数是否在合理范围、DDP 的卡数够不够。有问题的直接拒绝启动。

几个默认值值得说明：

- 随机裁剪的 scale 0.70~1.0，ratio 0.90~1.12。胸廓比例是固定的，不该像自然图像那样抖到 3:4。
- 归一化用 `(0.5, 0.5, 0.5)`，不是 ImageNet 那组。不用别人的权重，就没理由用别人的统计量。
- `drop_path`、`mixup_p`、`label_smoothing` 默认全关。这三个强度必须按数据量调，`scratch_strong.yaml` 里才一起打开。
- `train.resume: true`。断点续训是默认行为，所以换实验必须换 `run_name`，否则会接着旧断点往下跑。

机器档位只有三项差别：

| 档位 | workers | 混合精度 | 编译 | 用在哪 |
| --- | --- | --- | --- | --- |
| `mps_tiny` | 0 | 关 | 关 | 本机 Apple Silicon |
| `cuda_full` | 8 | bf16 | 关 | 比赛的单卡 |
| `cuda_ensemble` | 8 | bf16 | 开 | 集成阶段 |

MPS 的限制是硬的：不能多进程取数，没有混合精度，不能编译。这些不在每个配方里重复写，统一在 `config/devices.py` 里按设备钳住。换机器只改一行。

## 四、数据怎么进模型

```mermaid
flowchart LR
  CSV["train.csv / valid.csv"] --> NORM["认列名<br/>几种写法都试"]
  NORM --> MAP["认类别号<br/>从 1 开始"]
  MAP --> UNION["按 study 合并标签"]
  UNION --> DS["数据集<br/>一张图一条"]
  DS --> TF["增强"]
  TF --> COLLATE["拼成 batch"]
  COLLATE --> BATCH["图 + 标签 + study 号"]
```

几条写死的约定：

**列号按类别号定位，不重新编号。** 如果一批数据只出现 5 个类，内部压成 5 列，训练和提交的列序就分叉了。所以训练定死顺序，验证和推理必须显式传 `class_ids`，不靠猜。

**类别号显式写成 1 起始。** 官方是 1..10。自动推断在数值重合时会出歧义，不值得冒险。

**标签按 study 合并。** 一个 study 几张图，任一张报了这个征象，这个 study 就算有。训练用单图标签，评测和推理用 study 标签。

**study 怎么合并有三种算法：**

| 算法 | 做法 | 什么时候用 |
| --- | --- | --- |
| `mean` | 概率直接平均 | 默认。图的质量差不多时最稳 |
| `logit_mean` | 先转成 logit 再平均 | 概率贴 0 或 1 时，避免被一张极端图拉平 |
| `max` | 取最大 | 只在"任一张有就算有"时用，结果会偏高 |

**study 清单是准的。** 合并结果严格等于传进去的清单。清单外多出来的预测忽略并提醒，清单里没有图的 study 填先验值。少了这条，提交缺行要到上传后才发现。

**先查患者泄漏。** 训练集和验证集按患者分，同一个人的图不能两边都有。如果官方切分没做干净，本地分数会虚高，早停会停在错的位置，而这个错在提交前看不出来。K 折同理，按患者分，不按 study 分。

## 五、模型长什么样

骨干是 torchvision 的 DenseNet121，改了三处：

| 改动 | 原来 | 现在 | 为什么 |
| --- | --- | --- | --- |
| 第一层卷积 | 3 通道输入 | 1 通道输入 | 灰度图直接进。没有预训练权重，就没必要复制成 3 通道 |
| 池化 | 固定 7×7 | 自适应到 1×1 | 224 / 320 / 448 同一份代码都能跑 |
| 分类头 | 1000 类 | 10 类 | 单层线性；要隐藏层就插一层 |

输出是 10 个 logits，不接 sigmoid。sigmoid 放在损失和推理里各做一次，模型只输出原始分数。

实测：

| 项 | 值 |
| --- | --- |
| 参数量 | 6.96M |
| fp32 体积 | 26.5 MB（上限 500MB，余量很大） |
| 单张前向（本机 CPU） | 224 输入 30.9 ms，320 输入 49.0 ms |

CPU 的数字不能当 T4 的延迟，但它说明这个规模不会卡在速度上。

### 初始化

从零训练时，初始化是唯一能免费塞进先验的地方。

- 卷积和线性层用 Kaiming 正态，按 fan_out 算。每个卷积后面都跟 BN，这个版本比 PyTorch 默认的更合适。
- BN 的权重设 1、偏置设 0。
- 分类头权重设 0，偏置设成 `log(p/(1-p))`，p 是这个类在训练集里出现的比例。
- 偏置再夹到 ±6.0。极端不平衡时 `log(p/(1-p))` 会到 -9，配上零权重会让这部分梯度长期卡在很小的值。

头两件事合起来：训练第 0 步，模型输出就是"按类别比例猜"。不花钱，但省掉开局把偏置推到位的几十步。

### 随机深度

按层深线性铺开：第一层不丢，最后一层丢到设定值。

实现上把它挂成 `_DenseLayer` 的子模块。这一点必须做对：只留 hook 闭包的话，`.eval()` 传不到它，推理时还在随机丢分支，同一张图两次预测不一样，而且完全不报错。挂成子模块后，断点里的键名不变，开关它不会让旧断点失效。

### 损失

四种，同一个接口，共用标签平滑：

| 类型 | 做法 | 参数 |
| --- | --- | --- |
| `bce` | 标准二元交叉熵 | — |
| `bce_posw` | 交叉熵乘逐类正样本权重 | 权重 = 负/正，夹在 `[1e-3, 20]` |
| `focal` | 难样本加权 | γ=2.0 |
| `asl` | 正负样本不同 γ，负样本概率先平移 | γ_pos=0、γ_neg=4、clip=0.05 |

标签平滑把目标从 1 改成 1-ε/2。官方标签来自报告"正面提及"，漏标比误标常见，软一点更贴合噪声。

正样本权重必须设上限。稀有类的正例可能只有个位数，负/正会到几百，不夹住的话一个 batch 就能把训练带崩。

ASL 和正样本权重同时开，等于正类被加权两次。所以 `scratch_strong.yaml` 把上限从 20 降到 10。真出现稀有类变差，第一步是把正样本权重整个关掉。

### 增强

只用 `torchvision.transforms.v2`，不引 albumentations。少一个依赖，离线环境少一类问题。

顺序是：转单通道 → 随机裁剪缩放到目标尺寸 → 水平翻转（0.5）→ 旋转 ±10° → 平移（0.05）→ 亮度对比度抖动（各 0.2）→ 转 float → 随机擦除（0.1）→ 归一化。

不做色相饱和度，灰度图没有意义。

MixUp 和 CutMix 是整批一起做，在拼好 batch 之后、前向之前，不在上面这条链里。

MixUp 在多标签下的做法是：同一个 λ 混图，也同一个 λ 混标签。λ 从 `Beta(0.4, 0.4)` 采。这里别照抄论文的 0.2：`Beta(0.2,0.2)` 是 U 形，实测 λ 会掉到 0.006，等于整批换成另一个样本，学不到插值。0.4~1.0 才合适。

CutMix 的 λ 按实际贴上去的面积重算，不是直接拿采样值当面积比。

## 六、一次训练做什么

```mermaid
flowchart TB
  A["取一批"] --> B["MixUp / CutMix<br/>按概率决定做不做"]
  B --> C["前向 · bf16"]
  C --> D["10 个 logits"]
  D --> E["算损失"]
  E --> F["反传 · 按累积步数"]
  F --> G["梯度裁剪 1.0"]
  G --> H["更新权重"]
  H --> I["更新学习率"]
  I --> J["更新 EMA"]
```

**优化器分组。** AdamW，参数最多分 4 组：分类头和主干，各自再分衰减与不衰减。判定是维度 ≤1 或者名字以 `.bias` 结尾就不衰减。

原因很直接：AdamW 的衰减是解耦的，对 BN 的尺度参数做衰减，等于把它往 0 拽，直接削弱归一化层的表达能力。这是从零训练里少有的纯赚改动。

**学习率。** 先线性升温两个 epoch，再按余弦降到接近 0。按 step 算，不按 epoch 算。早期 BN 的统计量还没稳，一上来用 3e-4 容易落进坏解。

**EMA。** 对所有权重和 BN 的统计量做滑动平均，decay 0.9998，前 100 次更新慢慢升到目标值。排序指标对权重抖动敏感，EMA 通常比最后一个 epoch 更稳。它单独存成 `best_ema.pt`，不覆盖 `best.pt`。

**早停。** 看 `macro_auc`，耐心 8 个 epoch，权重保留前 2 名，剩下的快照在训练结束时删掉。

**多卡。** 几条硬规定：

| 项 | 规定 |
| --- | --- |
| 启动方式 | 按 `torchrun` 的环境变量起子进程 |
| 通信后端 | CUDA 用 nccl，其余用 gloo |
| 数据切分 | 每个 epoch 手动推进 sampler，否则每次划分都一样 |
| 验证集 | 各卡分别推理，汇总后统一算指标 |
| 写文件 | 只有 0 号进程写断点和日志 |
| 冻结主干 | 冻结时开 `find_unused_parameters` |
| 随机种子 | 各卡错开，否则每张卡的增强完全一样 |
| MPS | 直接拒绝，多卡自测用 CPU + gloo |

多卡任务只能放在同一台机器上。梯度同步靠本机 NCCL，跨机器不成立。所以调度器把"一台机器"当分配单位，凑不齐就整单排队。

## 七、断点里有什么

格式标识 `csd-checkpoint-v1`，就是一个字典：

| 键 | 内容 |
| --- | --- |
| `meta` | 模型配置、预处理配置、类别号、类别名、元数据词表、合并算法 |
| `model` | 裸 state_dict |
| `epoch` `metrics` `ema_applied` | 训练到哪、上轮指标 |
| `optimizer` `scheduler` `ema` | 只在续训时写 |

三条规矩：

- **只存 state_dict，不 pickle 整个模型。** 本机 torch 比比赛容器新，pickle 过去的对象在容器里加载不了，state_dict 不会。加载时缺键只提醒，不直接崩。
- **meta 里的预处理配置是推理的唯一依据。** 这样 224 和 320 的模型能混着集成。少这一层，就得靠"记得当时用的哪个配置"，而人一定会记错。
- **存之前把包装剥掉。** DDP 包一层、编译再包一层，直接存会得到 `module._orig_mod.xxx` 这种带前缀的键名，换台机器就读不出来。

## 八、从图到提交文件

```mermaid
flowchart LR
  CK["断点"] --> TTA["几套 TTA<br/>原图 / 翻转 / 多尺度"]
  TTA --> P1["单个模型内平均"]
  P1 --> P2["跨模型平均<br/>可加权"]
  P2 --> AGG["按 study 合并"]
  AGG --> CSV["submission.csv"]
  AGG --> NPY["概率 .npy + 清单 .txt"]
  CSV --> VAL["查格式"]
```

**平均在概率上做，不在权重上做。** 权重平均要求几个模型在同一条损失曲面上，从零训练的不同配方不满足这个条件，平均出来往往比任何一个都差，所以不做。

**三类产物一起写。** csv 是提交物，npy 和 txt 是 study 级概率和清单。后者是为了"一张卡一个折"的跑法：那时没有进程同时拿着 N 个模型，为了集成再跑一遍推理纯属浪费。有了概率落盘，`scripts/merge_study_probs.py` 在 CPU 上按 study 名对齐求平均，几秒完成，结果可复现。

**每份概率必须覆盖同一批 study。** 少一个就是提交缺行，脚本直接报错，不取交集——取交集等于悄悄丢数据。

提交固定五列：

| 列 | 是什么 | 要求 |
| --- | --- | --- |
| `Subject_id` | 患者号 | 和测试表一致 |
| `Study_id` | 检查号 | 零填充字符串，绝不按数字解析 |
| `Predict_class` | 类别号 | 1..10，每个 study 出满 10 行 |
| `Probability` | 概率 | 落在 `[0,1]`；超过 1 基本是把 logits 写进去了 |
| `Gate` | 阈值 | 留空表示用默认阈值 |

写文件是先写临时文件再改名，中途失败不会留半个文件。写完查这几项：表头与列数、类别是否齐、患者号是否冲突、概率是否越界、有没有重复行、Gate 是否合法。

推理前还有一道预算检查：模型总体积不超过 500MB，单张不超过 100ms。DenseNet121 是 26.5MB，体积能放下十几个，真正卡住集成规模的是速度。

## 九、调度服务：三种放法

单卡跑一个配方很快。真正要跑的是"多组参数 × 多折"，手动开终端会乱。所以把"跑什么"和"在哪跑"拆开，中间放一层调度。

两种并行同时存在，不能混：

- **任务级并行**（默认）：一个任务占一张卡，产物是各自的 `runs/<run_name>/`。适合扫参数、跑多折。
- **单任务多卡**（`--gpus N`）：一个任务占 N 张同机卡，进程内同步同一份权重，只出一份 `best.pt`。这不是集成，是一个更大的 batch。

两种能混用：4 卡机器上跑两个 `--gpus 2` 的任务，各出各的模型。

### 放法一：都在本机

```mermaid
flowchart TB
  subgraph SUBMIT["提交"]
    J1["任务 A · 224 配方"]
    J2["任务 B · 320 配方"]
    J3["任务 C · 2 卡"]
  end
  subgraph SCH["调度器"]
    Q["队列<br/>优先级 + 提交时间"]
    SLOTS["分卡<br/>按运行中任务现算"]
  end
  subgraph HOST["同一台机器"]
    G0["卡 0"]
    G1["卡 1"]
    G2["卡 2"]
    G3["卡 3"]
  end
  J1 --> Q
  J2 --> Q
  J3 --> Q
  Q --> SLOTS
  SLOTS -->|"1 张"| G0
  SLOTS -->|"1 张"| G1
  SLOTS -->|"2 张 · 多卡"| G2
  SLOTS -->|"2 张 · 多卡"| G3
```

分卡不维护计数器，每次都从"正在运行的任务"现算。任务状态本来就落盘了，再存一份内存计数只是多一个会不同步的地方。不同步的表现是两张卡被派了三个任务，症状是莫名 OOM。

### 放法二：多机，主服务主动派

远程机器上跑一个同样的 `serve`。主服务把任务发过去，之后状态、日志、产物全代理回来。远程端不用改代码，代价是远程要有同一份代码和数据。

```mermaid
flowchart LR
  C["客户端"] -->|"提交"| S["主服务<br/>队列 + 设备表"]
  S -->|"起子进程"| L["本机卡 0"]
  S -->|"转发任务"| R1["节点 B · serve"]
  R1 -->|"起子进程"| B0["节点 B 卡 0"]
  S -->|"转发任务"| R2["节点 C · serve"]
  R2 -->|"起子进程"| C0["节点 C 卡 0"]
  R1 -.->|"状态 / 日志 / 产物"| S
  R2 -.->|"状态 / 日志 / 产物"| S
```

派发时只能发相对路径。两台机器的绝对路径不一样，发绝对路径过去，对方只会回"配置文件不存在"，而且是在任务已经显示"运行中"之后才失败。

多卡任务派到远程时不指定具体哪几张，只说"要几张"，由远程自己的设备表挑。主服务这边的记录只负责算"这台机器被占了几张"。

### 放法三：拉取节点，让 worker 主动来

前两种都要求主服务能连到节点。校园网、NAT、容器网络下经常不成立。拉取节点反过来：worker 自己来注册、领任务、回传。

```mermaid
flowchart LR
  subgraph INNER["内网 / NAT 后"]
    W["worker"]
    WG["本机卡"]
  end
  subgraph OUTER["公网可达"]
    S["主服务"]
    Q["任务队列"]
  end
  W -->|"1 注册"| S
  W -->|"2 心跳 + 领任务"| S
  S -->|"3 发任务"| W
  W -->|"4 增量日志"| S
  W -->|"5 回传产物"| S
  W -->|"6 报结果"| S
  W --> WG
  Q --> S
```

五个接口，全是 worker 发起：

| 接口 | 做什么 |
| --- | --- |
| `/pull/join` | 注册，报有几张卡 |
| `/pull/poll` | 心跳、领任务、看有没有被取消 |
| `/pull/log` | 补日志 |
| `/pull/artifact` | 传产物 |
| `/pull/finish` | 报状态、退出码、指标 |

失联按心跳算：30 秒没动静就不再派新任务，120 秒判为 `lost`。中间这段时间任务仍显示运行中——它确实可能还在跑。

取消也靠轮询：主服务在任务上打个标记，worker 下次心跳取走，自己在本地杀进程组。没有反向通道，就不可能有"推送取消"。

三种放法对比：

| | 本机 | 远程节点 | 拉取节点 |
| --- | --- | --- | --- |
| 谁发起连接 | 不用连 | 主服务 → 节点 | worker → 主服务 |
| 用在哪 | 本机卡 | 主服务能连到对方 | NAT 后、网络隔离 |
| 怎么判失联 | 进程退出就知道 | 连续轮询失败 | 心跳断了 120 秒 |
| 日志与产物 | 直接读 | 主服务代理 | worker 传上来再读 |

任务有六个状态：排队、运行中、成功、失败、取消、失联。

失联和失败要分开。失联只说明"不知道结果"，不代表训练挂了。服务重启后，远程任务和拉取任务都会被拉回运行中重新接管，再由心跳给出真实结论。

三件和进程有关的事：

- **用 `CUDA_VISIBLE_DEVICES` 屏蔽，不传 `cuda:1`。** 训练进程只看得到分给它的卡，代码里任何 `device="cuda"` 都落到对的位置。也就不存在"某处漏改 `cuda:0`，两个任务挤到同一张卡"。
- **子进程单独开一个进程组，取消时杀整组。** 训练会 fork 取数进程，多卡还会再起 N-1 个子进程。只杀父进程会留下孤儿占着显存，后面的任务全 OOM，现象是"新任务莫名失败"。这两个子进程继承同一个进程组，一次带走；10 秒不退再强杀。
- **结果看 `summary.json`，不看退出码。** `exit=0` 不代表真训了东西。

## 十、网页和接口

网页和命令行走同一套 HTTP 接口。服务端是纯标准库的 `ThreadingHTTPServer`，没有 Flask 或 FastAPI。

| 方法 | 路径 | 做什么 |
| --- | --- | --- |
| GET | `/` | 控制台页面（鉴权前放行） |
| GET | `/health` | 概览、设备占用、队列数 |
| GET | `/jobs` `/jobs/{id}` | 任务列表、单个任务 |
| GET | `/jobs/{id}/log` | 日志尾部 |
| GET | `/jobs/{id}/artifacts` | 产物列表与下载 |
| POST | `/jobs` | 提交任务 |
| POST | `/jobs/{id}/rerun` | 用同样参数再提交 |
| DELETE | `/jobs/{id}` | 取消 |
| POST/PATCH/DELETE | `/devices` | 增删改设备、探测 |
| POST | `/pull/*` | 拉取节点的五个接口 |

网页能触发的命令和参数，全部登记在 `server/commands.py` 一张表里，一共 9 条命令、15 个参数。每条命令说明四件事：要不要配置、产物是否按 run_name 落目录、产物落在哪、能不能多卡。没登记的键直接报错。

值的检查不复杂，但每条都有原因：

| 规则 | 为什么 |
| --- | --- |
| 不许换行 | 换行能拼出第二条命令 |
| 不许以 `-` 开头 | `--ckpt --help` 等于绕过白名单塞新选项 |
| 路径必须是项目内相对路径 | 客户端不该能读服务器上任意文件 |
| 枚举和数值要有范围 | 写错的参数要在提交时就说，不是跑完才说 |

产物也有白名单。训练任务能下载的只有 8 类：汇总、历史、配置、日志、三个权重文件、K 折汇总。推理任务是 `submissions/` 下的三类文件。这既是功能，也决定了"客户端能读服务器上哪些文件"。

网页是单文件，CSS 和 JS 全写在里面，不请求任何外部资源。内网没外网也照常显示，没有前端构建步骤。

几个取舍：

- **页面在鉴权之前放行。** 浏览器地址栏导航发不出鉴权头，拦掉首页只会让人看到浏览器的原生密码框，输完照样 401。页面本身是静态 HTML，不含数据，前端拿到 401 再弹输入框。
- **日志 2 秒轮询，不上长连接。** 任务状态是分钟级变化，多一条长连接只多一处会断的东西。
- **详情面板只在状态变化时重建。** 否则 2 秒一次的刷新会把正在看的日志滚回底部。
- **下载走 fetch 再转 blob。** 直接给链接带不上鉴权头。

前端不做业务校验。参数范围、路径、命令全在服务端判，页面只按类型出控件。

## 十一、怎么验证

381 项单测，本机跑约 30 秒。挑几个重点：

| 测试 | 管什么 | 关键断言 |
| --- | --- | --- |
| `test_losses.py` | 四种损失 | 结果与设备无关；权重上 CUDA 不炸 |
| `test_drop_path.py` | 随机深度 | 推理两次结果一致；断点键名不变 |
| `test_mixup.py` | MixUp / CutMix | λ 和标签一致；单样本批次跳过 |
| `test_optimizer.py` | 参数分组 | BN 和 bias 落在不衰减组 |
| `test_init_weights.py` | 初始化 | 头权重为零时 logits 等于先验 |
| `test_checkpoint.py` | 断点 | 只存权重；快照按指标删 |
| `test_distributed.py` | 多卡 | 真起两个进程跑一轮 |
| `test_server.py` | 调度 | 派发、取消、失联、产物白名单 |
| `test_pull_worker.py` | 拉取协议 | 领任务、取消、上传、重启后判失联 |
| `test_submission.py` | 提交格式 | 五列、类别齐、概率不越界、无重复 |

九步冒烟跑在合成数据上：

```mermaid
flowchart LR
  S1["合成数据"] --> S2["配置回显"] --> S3["患者泄漏检查"] --> S4["预缩放缓存"] --> S5["数据层自检"] --> S6["训练"] --> S7["验证"] --> S8["推理与提交"] --> S9["Gate 十行校验"]
```

合成数据是本地画的高斯亮斑，类别信息直接画进图里，所以模型学得动。这不是为了刷分，是为了证明标签、图像、增强、损失、合并、提交这条链上没有错位：AUC 落在 0.5 附近，说明标签和图对不上；能到 0.63，说明整条链是通的。

本机 MPS 上九步跑完 34 秒，`best macro_auc=0.6298`，提交 12 个 study、120 行、每个 study 正好 10 行。这些数字没有实战意义，价值在于可复现：换一台机器跑同一条命令，得到同一组数，说明没有哪一步偷偷依赖本机状态。
