上一篇把发送做通了：跑一条命令，微信把消息送出去。这一篇写它为什么最后还是被我关掉。

结论先摆出来：**单次发送能成功，但只要注入挂着，微信自己的发送就不稳定**。用户点发送转圈、消息不刷新、日志里连任务都没捕获到。撤掉注入、重新登录，一切恢复正常。这种「能用一次」的东西不能留在生产里。

## 一、先把崩溃查清楚

之前的现象是发送成功之后微信 SIGSEGV，崩溃点固定为 `wechat.dylib+0x41401a4`。反汇编出来是这样：

```asm
0x414019c  mov  x9, x23
0x41401a0  ldr  x8, [x9, #0x10]   ; parent = node->parent
0x41401a4  ldr  x10, [x8]         ; x8 = 0，崩在这里
0x41401b0  b.ne 0x41401a0         ; 沿 parent 上溯
```

这是 `std::map` 迭代器找后继的写法。`node->parent` 是 NULL，说明树坏了。

再往前追 `req2buf` 入口：

```asm
0x413e9b4  ldr x9, [x24, #0x60]!  ; map 根节点
0x413e9c0  ldr w10, [x9, #0x20]   ; 节点里的 taskId
0x413e9d4  cbnz x9, 0x413e9c0     ; lower_bound
0x413ea1c  ldr x0, [x23, #0x28]   ; 查到的节点里取消息对象
```

`x24+0x60` 是任务 map 的红黑树 root，不是消息槽位。之前的做法把它换成一个伪造节点：`+0x20` 填 taskId、`+0x28` 填消息指针。lower_bound 恰好会落到这个假节点上，所以编码、发送全都走通——**能发出去，正是因为假节点伪装成了树节点**。

代价是整棵树被替换掉了。之后任何一次遍历、插入、erase 都可能踩到空 parent，于是崩在 `0x41401a4`。

## 二、补齐缺失的那一步

导语里提过，微信的登记函数是 `0x413db60(service, msg)`。反汇编它：

```asm
0x413db60  ; x0 = service, x1 = msg
0x413dbd8  ldr  w1, [x20, #0xc]   ; 读 msg 的 cmdId
0x413dc1c  ldr  w23, [sp, #0xb0]  ; 新分配的 taskId
0x413dc20  str  w23, [x20, #8]    ; 写回 msg+0x08
0x413dc28  ldr  x8, [x25, #0x60]! ; 找到 service+0x60 的 map，插入节点
```

它自己分配 taskId、写回 `msg+0x08`、把节点插进树里。树由它维护，不会坏。调它登记，再用同一个 taskId 调 `MMStartTask`，整条链都是原生路径，不需要动 root。

这里踩了两个坑。

**service 不能从 `manager+0x18` 推。** `MMStartTask` 里确实有 `ldr x20, [x20, #0x18]`，但那个对象和登记函数要的 service 不是一个：实测前者是 `0xb871e2800`，后者是 `0xb86e60318`。混用会在登记函数开头 `ldarb [service+0x18]` 处直接访问违规。

**不能在 frida 自己的线程里调登记函数。** 换成真实 service 之后能走过 entry 和字符串拷贝，但崩在 taskId 生成器（`0x413dc14 blr x8`）——那一步依赖微信线程里的上下文。可行的做法是「搭车」：在微信自己调用登记函数时顺手做我们的事。

## 三、搭车点选错，直接把微信堵死

搭车有两个候选位置：登记函数的 hook，或者 `MMStartTask` 的 hook。前者频率太低（心跳复用已有节点，不重新登记），后者频繁。

我先选了后者，挂在 **onEnter** 上。结果是灾难性的：

```js
// 错误示范
onEnter: function () {
    register(service, myMsg);   // 我们登记
    MMStartTask(manager, task); // 我们在 MMStartTask 内部又调了一次 MMStartTask
}
```

`MMStartTask` 内部持有一把非递归锁。在它的 onEnter 里再调它自己，锁不会重入，原调用永远不返回。表现就是用户点发送之后一直转圈，消息既不出去也不刷新，日志里连 `StartTask` 捕获都看不到——请求根本没走到发送阶段。

改到 `onLeave` 之后不会死锁，因为原调用已经返回、锁已释放。但问题没有到此为止。

## 四、真正的问题：hook 面太宽

为了让「借壳发送」成立，脚本在五个点上挂了 `Interceptor.attach`：

| 位置 | 偏移 | 作用 |
|---|---|---|
| `MMStartTask` | `0x53e4ecc` | 抓载体、搭车 |
| `req2buf` 入口 | `0x413e9b4` | 按 taskId 定位 |
| 消息对象读取 | `0x413ea1c` | 换节点里的消息指针 |
| `blr x8` | `0x413ea34` | 接管编码，写自己的 protobuf |
| 任务登记 | `0x413db60` | 取真实 service、抓消息模板 |

除了最后两个，前三个都在每个请求必经的热路径上。任何一处回调里抛异常、卡住、或者时序踩到，都会影响 mars 任务泵。

对照实验很清楚：

- 23:32 重登后，**零注入**：`aaa`、`test` 两条都正常发出并同步入库
- 23:34 之后挂上注入：`test2` 转圈，`sss` 既不刷新也不入库，日志零 `StartTask`
- 23:44 撤掉注入：微信恢复

同类问题还出现过一次：多个 frida 会话同时 attach 同一个微信进程，mars 任务泵直接跑到 CPU 200%，detach 都救不回来，只能重启进程。

## 五、可用的标准

「能发出去一条」不算可用。可用的门槛应该包括：

1. 注入期间，用户手动发消息必须正常，延迟不能有可观测变化
2. 连续发送不崩、不卡、不漏
3. 注入可以随时卸掉，卸掉后微信完好

按这个标准，前一篇文章那套方案是不合格的：它连第 1 条都过不了。

## 六、如果还要继续

下一步不是继续加功能，是把 hook 收窄到能共存为止。验证顺序：

1. 只挂 `attachRealMsgCapture`（只读，读登记时的消息对象）+ `MMStartTask.onLeave`（搭车），手发十条消息，确认零影响
2. 加 `register` 的只读捕获，再回归一次手发
3. 加 `0x413ea1c` 的消息指针替换，再回归
4. 最后才加 `blr x8` 编码接管

每加一个点都要重跑「手动发消息 → 看是否入库」这条回归。任何一步出现转圈，就说明这个点不能常驻，得改成「用时挂、用完卸」。

如果收窄到最后仍然冲突，那这条路就该放弃。微信的发送链是它自己的关键路径，长期往里挂五个钩子，本身就是在赌它永远不出意外。

## 七、顺带确认的两件事

**版本边界**：这套东西只对 4.1.12 成立。4.1.13 的发送链是协程加一次性上下文，地址表全换，思路平移不过去。

**服务端会拒绝老版本**：当晚还出现过「消息发不出去、被吞掉」的情况。手机能发、Mac 不能，重登之后恢复。腾讯对旧客户端的态度是会变的，把生产链路压在某个具体小版本上，等于把可用性交给对方。

这两个约束叠起来看，自主发送这条路的维护成本，比它省下的那点手工操作高得多。
